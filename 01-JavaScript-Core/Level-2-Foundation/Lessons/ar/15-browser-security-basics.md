## 🎯 1. نظرة عامة وأهداف التعلم (Overview & Learning Objectives)

متصفح الويب هو بيئة تشغيل عدائية بطبيعتها؛ فهو ينفذ في نفس الوقت أكواد موقعك البنكي، وشبكات التواصل الاجتماعي، وشبكات الإعلانات الخارجية غير الموثوقة، وجميعها تتشارك نفس الشاشة والذاكرة الفيزيائية للجهاز.

لمنع الأكواد الخبيثة من سرقة بيانات المستخدمين وجلساتهم الخاصة، يعتمد الويب على حواجز أمان معمارية حاسمة: **سياسة الأصل المشترك (Same-Origin Policy - SOP)** ونظام **مشاركة الموارد عبر النطاقات (CORS)**.

بنهاية هذا الدرس، ستتقن:
1. الحساب الرياضي الدقيق لـ **الأصل (Web Origin)** الثلاثي (`البروتوكول` + `المضيف` + `المنفذ`).
2. ما تحميه وما تفرضه **سياسة الأصل المشترك (SOP)**.
3. كيفية عمل نظام **CORS**: الطلبات البسيطة، طلبات الفحص المسبق (`OPTIONS`)، والترويسات المسؤولة.
4. الفهم الخاطئ الشائع لدى المطورين حول الجهة المسؤولة عن فرض قواعد الـ CORS.
5. تأمين مكتبات الطرف الثالث باستخدام خاصية **تكامل الموارد الفرعية (Subresource Integrity - SRI)**.
6. الأساسيات الدفاعية لترويسة **سياسة أمان المحتوى (Content Security Policy - CSP)**.

---

## 🌐 2. تحديد أصل الويب (Web Origin) بدقة

يُعرّف **الأصل (Origin)** حصرياً بتطابق ثلاثة عناصر متتالية:

```
  https :// example.com : 443
  \___/     \_________/   \__/
البروتوكول    المضيف     المنفذ
```

إذا اختلف **أي جزء واحد فقط** من هذه الأجزاء الثلاثة، فإن الرابطين ينتميان إلى **أصلين مختلفين تماماً**:

### مصفوفة مقارنة الأصول (مقارنة بالرابط `http://example.com/app`):

| الرابط المستهدف | هل هو نفس الأصل؟ | السبب |
| :--- | :---: | :--- |
| `http://example.com/other/page` | ✅ **نعم** | تطابق تام: البروتوكول (`http`)، المضيف (`example.com`)، والمنفذ (`80`) |
| `https://example.com/app` | ❌ **لا** | اختلاف في البروتوكول (`http` مقابل `https`) |
| `http://example.com:8080/app` | ❌ **لا** | اختلاف في المنفذ (`80` مقابل `8080`) |
| `http://api.example.com/app` | ❌ **لا** | اختلاف في المضيف (النطاق الفرعي `api.` مضيف مستقل) |

## 🛡️ 3. سياسة الأصل المشترك (Same-Origin Policy - SOP)

تعتبر **سياسة الأصل المشترك** حجر الزاوية لأمان شبكة الويب؛ فهي تمنع كود جافا سكريبت يعمل على موقع خبيث `https://attacker.com` من قراءة أو استخراج البيانات السرية الخاصة بلسان تبويب `https://bank.com`.

### ما الذي تمنعه وتفرضه سياسة الـ SOP؟
1. **الوصول لشجرة عناصر الـ DOM:** لا يستطيع كود داخل `iframe` قراءة عناصر أو نماذج صفحة أخرى تنتمي لأصل مختلف.
2. **عزل التخزين المحلي:** وحدات التخزين `localStorage` و `sessionStorage` و `IndexedDB` معزولة تماماً لكل أصل على حدة.
3. **منع قراءة استجابات الشبكة:** يمكن للموقع إرسال طلبات لأصول خارجية (مثل عرض صورة أو إرسال نموذج)، لكن كود جافا سكريبت **عاجز تماماً عن قراءة جسم الاستجابة (Response Body)** ما لم يوافق الخادم صراحة.

## 🔄 4. مشاركة الموارد عبر الأصول (CORS)

تفصل التطبيقات الحديثة عادة بين واجهة المستخدم (`https://app.example.com`) والخادم البرمجي (`https://api.example.com`). ونظراً لاختلاف النطاق الفرعي، يمنع المتصفح الواجهة من قراءة بيانات الـ API تحت مظلة الـ SOP.

نظام **CORS** هو آلية تعتمد على ترويسات الـ HTTP تسمح للخادم بإعلام المتصفح صراحة بالسماح لأصول معينة بقراءة بياناته.

```
[ الواجهة الأمامية (https://app.com) ]                [ خادم الـ API (https://api.com) ]
              |                                                   |
              | --- 1. GET /data (Origin: https://app.com) -----> |
              |                                                   |
              | <--- 2. Access-Control-Allow-Origin: https://app.com |
              v                                                   v
   يتأكد المتصفح من مطابقة الترويسة ➔ ويسلم البيانات لكود جافا سكريبت!
```

### طلب الفحص المسبق (Preflight Request: `OPTIONS`):
عندما يستخدم الطلب عمليات غير تقليدية (`PUT`, `DELETE`) أو ترويسات مخصصة (`Content-Type: application/json` أو `Authorization`)، يرسل المتصفح تلقائياً طلب فحص مسبق بنوع **`OPTIONS`** قبل إرسال الطلب الفعلي:

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization
```

يجب أن يرد الخادم بترويسات الموافقة الرسمية:
```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

> [!IMPORTANT]
> **الفهم الخاطئ الأكبر حول الـ CORS:**  
> قواعد الـ CORS **يفرضها المتصفح لحماية المستخدمين**، وليس الخادم لحماية نفسه!  
> يستطيع أي مهاجم إرسال طلبات مباشرة للخادم باستخدام أدوات مثل `curl` أو بايثون وتجاوز الـ CORS تماماً؛ لأن الـ CORS وجد لمنع المواقع الخبيثة من استغلال متصفح الضحية لقراءة بياناته الحساسة دون علمه.

## 📦 5. سكربتات الطرف الثالث وتكامل الموارد الفرعية (SRI)

عندما تضمن مكتبة خارجية عبر شبكة توزيع محتوى (CDN):
```html
<script src="https://cdn.example.com/library.js"></script>
```
فإن هذا السكربت الخارجي يعمل **بكامل صلاحيات موقعك وأصلك البرمجي**! وإذا تم اختراق خادم الـ CDN، يستطيع المهاجمون حقن أكواد خبيثة لسرقة حسابات كل زوار موقعك.

### الحل الدفاعي: تكامل الموارد الفرعية (Subresource Integrity - SRI)
تتيح ميزة الـ SRI للمتصفح التأكد من أن الملف المستلم يطابق تماماً البصمة الرقمية الأصلية ولم يتم التلاعب به:
```html
<script 
  src="https://cdn.example.com/library.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous">
</script>
```
إذا اختلف محتوى الملف ولو بحرف واحد، يفشل فحص التجزئة (Hash)، ويرفض المتصفح تشغيل السكربت تماماً!

## 🔒 6. أساسيات سياسة أمان المحتوى (Content Security Policy - CSP)

تعتبر **سياسة أمان المحتوى (CSP)** ترويسة HTTP أمنية بالغة القوة، تقيد الأماكن والمصادر التي يُسمح بتحميل وتشغيل الأكواد والوسائط منها:

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com;
```
- تمنع تشغيل الأكواد المضمنة السطحية (`<script>alert(1)</script>` أو `onclick="..."`).
- تمنع استيراد السكربتات من خوادم خارجية غير مصرح بها.
- تحد بشكل هائل من أضرار وخطر ثغرات حقن السكربتات (XSS).
